Stage1C design, not yet implementation:
- CAS revisioned field-level JSON patches preserve unknown config fields and eliminate stale cross-service merges. SQL reads verify revision; no process TTL authority.
- Shared member row lock serializes warning insertion/removal/threshold claims and restriction transitions. A claimed warning generation creates one durable sanction intent; reset only through its cutoff after complete primary action. Unknown external completion stays uncertain rather than blindly replaying.
- SQL challenges bind generation, actual message/thread/applicant, immutable issued mode/answer/attempt budget/deadline and policy. Answer/timeout claim one pending generation. Redis legacy pending imports are bounded by known identities, not KEYS; legacy callbacks must match their actual server-created message. Replacement fences stale callbacks/jobs.
- Durable job statuses pending/running/succeeded/failed/uncertain/cancelled; lease, bounded batches, retry schedule and precise ownership. Separate prepare vs external-dispatch boundary. Safe known errors retry with deadlines/backoff; expired dispatched lease becomes uncertain, not automatic repeat.
- Scoped restriction rows and per-member SQL guard prevent CAPTCHA release from removing another manual/fed/newcomer restriction. Night snapshot becomes durable SQL state; ownership restoration verifies current closed state and does not override later changed permissions. Child pause/delete invokes scoped pre-transition cleanup; no sibling grants.
- Group Guard inbox persists before webhook acknowledgement, claims updates once, tracks message content versions without re-counting edits. Incoming exact duplicate IDs/content suppress handlers; received work recovers; interrupted external delivery is explicit uncertainty. Retention is a local documented policy, not Rose behavior.
- PostgreSQL is concurrency authority; SQLite uses bounded in-process locks only for unit tests, clearly labeled. Actual distributed acceptance must use PostgreSQL/Redis.
